# RAVEN Architecture Review

This review is intended for developers continuing work on RAVEN. It separates code paths present in this repository from behaviors that still require platform/device validation.

## Architectural boundaries

```text
Screens (lib/screens)
    │ user actions / view state
    ▼
Services (lib/services) ───── OS/plugin APIs
    │                           ├─ microphone / encoder (record)
    │                           ├─ audio playback (just_audio)
    │                           ├─ private app directory (path_provider)
    │                           ├─ secure key storage (flutter_secure_storage)
    │                           └─ PDF, file picker, share/export
    ▼
ProjectRepository ── projects.json + backup/recovery + category manifests
    ▼
RavenProject / RavenAudioSession / RavenBookmark
```

## Source of truth and file layout

- `RavenProject.id` is stable and is not derived from title/category. Renaming changes metadata only; audio and master paths stay anchored under the UUID project directory.
- `projects.json` is the canonical index. Category manifests are derived indexes only.
- Audio sessions are stored beneath `projects/<project-id>/sessions/`; a category rename must not move audio.
- A recording creates a draft project before microphone capture begins so unexpected termination can leave recoverable metadata.
- Attachments are copied into the project's `attachments/` directory and filenames are sanitized.
- Project bundles include a JSON manifest plus project-relative files. Import is currently staged and validated by `ProjectArchiveService`; a user-facing final import/merge workflow still needs to be completed before calling import fully shipped.

## Error-handling rules

1. Never delete a source recording until its replacement has been fully written and the project index update succeeds.
2. Keep a backup before replacing the canonical project index.
3. A damaged individual project entry should not prevent loading other valid entries.
4. Never silently treat a decryption failure as playable audio.
5. Surface actionable, localized errors at the screen boundary; never log API keys, notes or audio contents.
6. On cancellation, do not create empty projects or empty attachment files.
7. Keep original audio separate from any generated transcript, notes, enhancement or AI output.

## Security review and limits

### Implemented foundation

- AES-256-GCM authenticated file encryption primitive with a random 256-bit key in OS secure storage.
- Ciphertext marker, nonce and authentication tag; authenticated decryption fails closed.
- Project player has an explicit encrypt/decrypt operation that writes all new outputs before changing the project paths, then best-effort deletes old files.
- API-key vault uses secure storage instead of ordinary preferences.

### Not yet a production security guarantee

- The audio encryption key is device/app scoped, not derived from a user password. Losing secure storage/app data can make ciphertext unrecoverable.
- The service reads an entire audio file into memory. Very long recordings need chunked authenticated encryption with a versioned file format.
- Playback uses a temporary plaintext file because the player plugin expects a file path. Cleanup is attempted on player teardown and file change, but process termination can leave a temporary copy. A startup cleanup sweep and app-lifecycle handling should be added; streaming decryption would be stronger if supported.
- Secure deletion cannot be guaranteed on flash storage.
- Exporting a protected project exports its ciphertext plus metadata. The receiving installation must have a compatible key-recovery design; this version does not implement portable password-based key wrapping.
- App-wide PIN/biometric lock and separate notes-vs-audio authentication are not complete. Do not advertise them as shipped.
- Do not use production-sensitive recordings to test encryption until the key/backup lifecycle has been validated on target devices.

## Compatibility and audio behavior

- The manifest targets Flutter `>=3.47.5` and Dart `>=3.5.0 <4.0.0`.
- `record` encoder and DSP support varies by platform. UI selections are not proof that every target supports each format. Confirm support and surface a fallback/error when an encoder cannot start.
- `autoGain`, `echoCancel`, and `noiseSuppress` are requests to the native recorder; results and support vary by OS/device.
- `just_audio`, `file_picker`, `printing`, secure storage and share behavior must be verified separately on Windows and Android.
- Windows desktop support needs the Windows runner generated by Flutter and Visual Studio's Desktop development with C++ workload.

Run from the project root using the requested Flutter SDK:

```powershell
flutter --version

flutter pub get
flutter analyze
flutter test
flutter run -d windows

```

Do not skip analyzer findings. Fix API incompatibilities instead of silencing lints globally. Run the Android app on a physical device to validate microphone permissions, background/foreground transitions, calls, low-storage conditions, encrypted playback and process termination.

## Continued recording semantics

- The project UUID is stable; each recording take/session receives a separate UUID and file.
- Continue recording is available from an existing unprotected project.
- Before capture begins, the repository stores a draft that includes the previous sessions plus the new session path. Successful stop updates only the new session's path/duration and clears the draft flag.
- A failed start or explicit discard restores the prior project snapshot and removes the partial session file without deleting the existing project.
- The project title is retained when continuing; it is never reset to a generated timestamp title.
- Protected projects are blocked from continuation until audio is decrypted, avoiding accidental mixing of encrypted and plaintext sessions.

## Security lifecycle additions

On application startup, a best-effort sweep removes stale `raven-playback-*` plaintext cache files from the platform temporary directory before the player can open. Player disposal also removes the active decrypted cache. This reduces exposure after abrupt termination but does not guarantee secure erasure on flash storage. Production hardening still requires lifecycle tests, protected-cache permissions, key backup/recovery design, and chunked encryption for long recordings; current AES-GCM processing reads a complete file into memory.

## October 2026 follow-up: master audio and optional AI

- A continued recording is first persisted as an internal source session. `AudioMergeService` then creates a new master using the maintained `ffmpeg_kit_flutter_new_audio` audio-only package. Source sessions remain available for recovery; playback prefers the master and falls back to the internal playlist when a master is missing or merge fails.
- Master replacement is performed through a pending output, and a master path is cleared before a continuation rebuild. Protected projects must not retain an unencrypted master: the player removes any stale master reference/file before opening protected source sessions. The merge service rejects `.ravenenc` inputs.
- The FFmpeg package is LGPL-3.0; review its license and preserve required notices when redistributing builds.
- `RavenAiProviderService` supports OpenRouter's OpenAI-compatible Chat Completions endpoint, OpenAI Chat Completions, and Gemini `generateContent`. Keys are read from `AiKeyVault`; model IDs are editable; network timeouts and prompt length are bounded; request failures avoid intentionally printing credentials.
- AI actions currently send only notes text after a confirmation dialog. Summaries, organization/polishing, and translation are user-triggered; generated output is reviewed before replacing notes and can be stored separately in project metadata. No audio transcription or automatic audio upload is implemented.
- This follow-up has only passed dependency-free structural checks in the current environment. Run `flutter pub get`, `dart format lib test`, `flutter analyze`, `flutter test`, and Android/Windows builds before treating it as release-ready. Specifically test FFmpeg filter behavior with M4A/WAV/FLAC sessions, long projects, paths containing spaces/non-ASCII characters, low disk space, interrupted merges, and protected-project transitions.
